EmbeddingDaemon.embedWithTimeout ignored request.kind and wrapped every request in disposingOnTimeout, which erased the rule with-timeout.ts documents explicitly: a query must never cost the worker its life, because the caller answers from FTS meanwhile and a model still loading after an idle-kill should finish for the next query instead of restarting. Combined with the acquisition budget it was also the mechanism that made a cold start unrecoverable inside the daemon — every tick discarded the partial model fetch.

A query now takes the plain withTimeout and a passage keeps the disposing one, so the daemon follows the same two rules as the in-process paths. The lane advances when the wrapper settles, which is what lets a timed-out query keep loading in the worker while the next request queues behind it in the worker itself.
