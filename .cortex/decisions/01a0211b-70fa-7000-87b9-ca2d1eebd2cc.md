openDecisionsDbReadOnly opens the store with { readwrite: true, create: false } and immediately runs PRAGMA query_only = ON. The obvious alternative — Database(path, { readonly: true }) — was rejected: a read-only handle on a WAL database cannot manage the write-ahead log, so it creates decisions.db-shm and decisions.db-wal on open and leaves both behind on close. A project the user only asked about would gain files it never had, which is exactly the harm the read-only fan-out exists to prevent. With query_only SQLite creates the same sidecars and deletes them again when the last connection closes, so the directory is left exactly as it was found.

query_only is a real guarantee, not a convention: SQLite answers SQLITE_READONLY to any write, so migrate, the bootstrap export and any repository insert fail rather than silently succeeding. The price is that a store on a genuinely read-only mount can no longer be opened at all; it is reported as skipped with its reason, which is the accepted trade-off.

prompt-hook keeps its own Database(..., { readonly: true }): it opens one store in a short-lived process and must never fail, and there is no fan-out promise to keep there.
