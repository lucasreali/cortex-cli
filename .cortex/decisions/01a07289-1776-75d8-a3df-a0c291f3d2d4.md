install.sh already had two guards: a CI step that sources it with CORTEX_SOURCE_ONLY=1 and compares detect_suffix against buildTarget() on the runner, and verify-darwin, which installs a published asset through the script a user would actually run. install.ps1 gets both, but the placement of the first one is the decision.

The parity check for install.ps1 lives in ci.yml's `windows` job — inside the gate release.yml calls — not in a job after the release. Nothing in the TypeScript suite can find a syntax error in a PowerShell file: only PowerShell parses it. Inside the gate that costs a failed build; discovered by verify-windows it would cost a published tag whose Windows installer nobody can run, and a tag cannot be un-published.

That job also compiles the binary and drives scripts/compiled-smoke.ts end to end on windows-latest — init, index, save_decision over MCP, embed through a self-spawned worker, semantic search, doctor. It deliberately does not run `bun test`. Linux stays the one platform the suite runs on; macOS and Windows get the compiled artifact exercised instead, which is the claim a cross-compiled binary actually has to support, and it is the same shape verify-darwin has always had.

verify-windows mirrors verify-darwin after the release: install through install.ps1, verify the Sigstore attestation on the published windows-x64 asset, then run the binary in a throwaway repo — with `install --git-hooks` added there, since Git for Windows' bundled sh is the one part of the hook path no Linux job can exercise.

tests/docs/release-workflow.test.ts asserts all of this from the YAML, so the arrangement cannot be quietly undone.
