writeAtomically and its sync twin staged a temp file next to the target path and renamed over it, doing neither of the two things graphify's _atomic_replace does. Both gaps were real: writing to a managed path that is a symlink replaced the link with a regular file, breaking worktree and shared-output setups, and a fresh staging file carried the process umask, silently tightening a destination someone had widened to group-readable.

Decided: resolve the leaf symlink chain BEFORE choosing the staging path, and copy the destination's permission bits onto the staging file before the rename.

The ordering is load-bearing and is the part worth remembering: resolving first is also what keeps the staging file on the target's filesystem, and rename is only atomic within one filesystem — which is the entire reason this module exists. Staging next to the link instead of next to the target could cross a mount boundary and lose atomicity.

Details: the chain stops after 40 hops, matching Linux's own limit, so a symlink cycle ends instead of spinning. An absent destination and a chmod we lack permission for share one catch, because both mean the same thing — leave the umask default alone rather than fail a write that would otherwise succeed. Both twins go through shared helpers; a divergence between the async and sync writers would be a real bug, since the sync one exists only because a bun:sqlite transaction cannot survive an await.

Accepted trade-off: cortex now writes THROUGH a symlink at a managed path rather than replacing it. install --git-hooks is unaffected — it already refuses a symlinked hook path before reaching the writer.
