Bun serves every module inside a compiled binary from an embedded filesystem and roots it differently per platform: "/$bunfs/" on POSIX, "B:\\~BUN\\root\\" on Windows — which reaches import.meta.url as file:///B:/~BUN/root/. The check was `import.meta.url.includes("$bunfs")`, written twice on purpose (embedding/subprocess-command.ts and release/target.ts each kept a copy so the upgrade path would not import the rest of the program), and both copies were wrong together. That is what a duplicated check buys: one bug in two places, with nothing comparing them.

A compiled Windows binary therefore read itself as a source checkout, and that single boolean decides five things:
- releaseOrigin honours CORTEX_RELEASE_BASE_URL — an installed binary would have downloaded, executed and installed over itself from any address an environment variable named.
- overriddenWorkerPath honours CORTEX_EMBED_WORKER_PATH — an installed binary would have spawned any script an environment variable named.
- upgradeTargetPath honours CORTEX_UPGRADE_TARGET_PATH and otherwise answers null, so `cortex upgrade` had nothing to replace.
- embedWorkerCommand and embedDaemonCommand spawn a .ts path derived from the module URL instead of the binary's own hidden subcommand, so on Windows they would have pointed at B:\\~BUN\\root\\worker.ts — embedding could never have started.
- selfCommand pins that same non-existent path into the git hooks it writes.

runsFromEmbeddedFilesystem now holds the recipe once, in support/ — which imports nothing, so release/ may depend on it without dragging anything in behind it, which was the whole reason for the second copy. It is pinned by example against both spellings and against real paths that merely resemble them, because the marker is a fact about another program's internals and cannot be derived here.

Found by scripts/compiled-smoke.ts on the first Windows CI run, at the second assertion. Nothing in the unit suite could have found it: from source the constant is false on every platform, which is the correct answer there, and only a compiled Windows binary can produce the URL that exposed the gap. This is the argument for driving the artifact end to end on each platform it is cross-compiled for rather than trusting the suite that never sees it.
