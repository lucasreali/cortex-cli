Both MCP upserts replaced the cortex entry wholesale, so a user who had added `env: {CORTEX_NO_USEFULNESS: "1"}` lost it on the next `cortex install`, with no diff and no warning, and the behaviour they were suppressing came back. Our keys now win and everything else on the entry survives: the JSON side merges the parsed entry under the rendered one, and the TOML side rebuilds the table from the merged object rather than from the spec, which is what carries `[mcp_servers.cortex.env]` back out.

Separately, writeAtomically guarantees that no reader sees a partial file; it guarantees nothing about a read-modify-write. ~/.claude.json holds per-project state, history and trust decisions and is rewritten continuously by the very session that runs `cortex install`, so publishing a copy rendered before that rewrite silently reverts it. writeAtomicallyIfUnchanged re-reads the destination once the staging file is complete and refuses the rename if it moved, which narrows the window from the whole read-merge-render-stage to the rename itself. It cannot close it — rename is not a compare-and-swap — and that is stated rather than hidden.

A lost race is retried three times, each attempt re-reading, so the merge lands on what the other writer left rather than on what we first read; after that the file is reported skipped with a reason instead of clobbered. The guarded write is a parameter of upsertJsonMcpServer with the real one as its default, which is where this module's I/O boundary sits and is what lets the lost-race path be exercised deterministically instead of by luck.
