RELEASE_SUFFIXES gains a single "windows-x64" entry. Bun cross-compiles no windows-arm64 build, and Windows on ARM runs an x64 image under emulation, so targetForHost answers "windows-x64" for win32 regardless of process.arch, and install.ps1's Get-Suffix answers the same for AMD64, ARM64 and a 32-bit shell on a 64-bit machine (PROCESSOR_ARCHITEW6432 set). A genuinely 32-bit Windows is refused; no asset exists for it.

No baseline variant, unlike linux-x64-baseline. Neither install.ps1 nor targetForHost can read a CPU feature list on Windows — there is no /proc/cpuinfo and no cheap PowerShell equivalent — so a baseline suffix would be one nothing could ever select, and RELEASE_SUFFIXES is the single list both sides compile from and select out of. A suffix that exists on only one side is exactly the drift the list was created to prevent.

Rejected: publishing a .zip for Windows. Keeping .tar.gz means one archive format, one checksums.txt discipline, one assetName rule and one in-process reader (src/release/archive.ts) for the upgrade path on every platform. tar.exe has shipped in Windows since 10 1803, which is the floor this release already sets.

The tarball's executable member is cortex.exe rather than cortex. scripts/compile.ts's executableNameFor spells it from the target rather than from the builder — Bun appends .exe to a Windows --compile outfile whether asked or not, and package-release.ts has to chmod, utimes and tar exactly the file that was written. readCortexBinary accepts either name, because which one arrives is a fact about the asset and not about the host unpacking it.
