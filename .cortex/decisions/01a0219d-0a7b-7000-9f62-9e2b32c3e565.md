Three defects in the file format, all of the same shape: something a foreign editor or a bad merge writes, silently changing what the store holds.

A UTF-8 BOM made a file unparseable — CRLF was normalized but U+FEFF was not, and splitFence requires the source to start with the fence. Cortex never writes one, but a Windows editor or a PowerShell redirection during a merge fix does, and the file is immutable once committed. normalizeSource strips it before anything else looks at the source.

A repeated frontmatter key resolved to the last one, which is exactly what a badly resolved merge conflict leaves behind: two title: lines, one silently winning and getting indexed. It is refused with "duplicate frontmatter key: <key>" rather than picked, because the file is on the branch either way and guessing is how the wrong decision gets indexed. The scan is over column-zero keys only, which is every key this format has.

The body was normalized only on the way in from the file, never on the save path, so the row and the file disagreed until the database was rebuilt — a fresh clone would read a body the machine that saved it never stored. normalizeBody is now one function called by both parseDecisionFile and toDecisionFile: the same recipe at both ends of the round trip, the way symbolKey is.

Also here: anchorInputSchema now refuses a file_path that escapes the repository (leading /, ~, a drive letter, or a .. segment). It only ever enabled existence probing, but an anchor is written into a file nothing rewrites, so a bad path stays there and every resolver probes outside the project on every run. parseDecisionFile stays permissive about it — shape only, never policy, or a file that predates the rule would vanish from the branch it lives on.
