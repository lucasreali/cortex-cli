The five writes behind a decision — node, anchors, FTS row, two local edges — are wrapped in a transaction inside DecisionSyncRepository, not in its callers. The reconcile path already had one; the save path did not, and insertFtsRow runs after insertAnchors, so any anchor failure committed the node row and skipped the FTS row. Nothing repaired it: reconcile only inserts ids absent from listPresence, and the broken id is present, so --full included no pass ever added the missing row. The decision sat on disk, listed by cortex log, and was permanently absent from FTS, from prompt-hook and from the bm25 leg of semantic search.

Because the reconcile wraps its own transaction, this nests as a SAVEPOINT — which is what makes the second half possible: a decision the store refuses is caught, reported as malformed with the file name and the SQLite message, and skipped, while every other decision in the pass still lands. Letting it propagate rolled the whole reconcile back, and since 'arriving' is recomputed from the same files on every run, the next command failed identically, forever, naming neither the file nor the reason.
