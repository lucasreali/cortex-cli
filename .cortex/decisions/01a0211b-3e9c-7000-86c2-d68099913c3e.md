search_all_projects and `cortex search --all-projects` declare readOnlyHint, and permission-gating clients run them without prompting — but the fan-out used to open a full CortexRuntime per root, which does mkdirSync, migrate(), exportDecisionsIfNeeded() (writing a markdown file per decision into that project's working tree for a pre-decisions/ store), writeConfig, a full reconcile and registerProject. One cross-project question therefore migrated, reconciled and possibly dirtied every repo on the machine.

The fan-out now goes through ProjectReader (src/app/project-reader.ts): a query_only connection, the three read repositories, and nothing else. No mkdir, no migrate, no bootstrap export, no reconcile, no registration, no code index, no embedding provider. A store behind SCHEMA_VERSION is reported under "skipped" with its reason instead of being silently upgraded, and the reader is closed in a finally, so a sweep returns to its baseline descriptor count.

Two consequences follow from the reader being synchronous and provider-less. The query is embedded once for the whole sweep and the vector is passed to each store (SemanticSearch.embedQuery + rank, split out of search), instead of each project's own SemanticSearch embedding the identical text behind one serialized daemon worker — 200 projects used to mean 200 embeddings. And the project label comes from the registry entry's canonical_id rather than from getCanonicalProjectId per root, which removes three blocking Bun.spawnSync git calls per project.

The sweep is bounded twice, because the registry grows without limit and a tool call the client times out on is worse than a narrowed answer: at most 50 roots are visited and a 10 s deadline stops the rest, both reported in the existing "skipped" shape. It stays sequential — the per-project work is synchronous, so concurrency would be theatre — but yields to the event loop between projects so the server's transport keeps answering.

QueryVector carries the model id with the vector: a store pinned to a different model holds no vectors under that id and degrades to FTS, which is correct rather than a failure.
