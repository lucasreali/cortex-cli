Both local sidecars — .cortex/local/usefulness.jsonl and the opt-in query log — are append-only JSONL with an occasional shortening pass, and both got the same two things wrong. src/support/append-only-log.ts is now the one implementation.

Ceiling from the data, not from a counter. QueryLog compacted every APPENDS_BETWEEN_COMPACTIONS appends, counted per instance. A CLI process makes one query and exits, so the counter never reached the trigger anywhere but a long-lived server: MAXIMUM_ENTRIES was not a ceiling at all on a file that holds the verbatim text of what was asked. The trigger is now one statSync per append against MAXIMUM_BYTES (1 MiB), and the ceiling counts bytes rather than rows — a thousand one-line questions and a thousand pasted stack traces are the same number of rows three orders of magnitude apart. Compaction trims to COMPACTED_BYTES (half the ceiling) rather than back to the trigger, so it is amortized instead of firing on every subsequent query; without that hysteresis a log sitting at the limit would read and rewrite itself once per query.

Compaction merges rather than replaces. Both logs did readFileSync, filter, renameSync, and the comment claimed the re-read protected a concurrent process's appends. It did not: anything appended between the read and the rename was replaced. compact() now re-reads before publishing and puts back the bytes past the offset it read, sliced on a Buffer so multi-byte lines survive intact.

No lock, on purpose. Closing the residual window (a line appended after the tail read and before the rename, microseconds) would need a lock the appenders also take, turning every query into an open, an exclusive create and an unlink — and trading this window for a stale lock that disables compaction outright, which is precisely the failure H17 fixed in the daemon. For a cache that costs nothing to rebuild that is the worse bargain, and the code says so where it happens.

UsefulnessEventLog keeps its own decoded cache but drops it after a compaction, because the merged tail means what is on disk is no longer what the instance believed.
