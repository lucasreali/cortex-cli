CORTEX_RELEASE_BASE_URL was honoured at runtime by the shipped binary, with no scheme check and no host allowlist. Both the asset and checksums.txt come from that origin, so verification only proved the attacker's tarball matched the attacker's digest, and installBinary executes the download for its version probe before renaming it over the running binary — which is also the MCP server every agent session spawns. Anything able to set an environment variable (a cloned repo's .envrc, a CI job, an MCP server env block) was persistent RCE.

releaseOrigin now takes the override only when the URL is https and its host is exactly github.com, and throws naming what it refused otherwise. A fork is still reachable; a plaintext or foreign host is not.

The gate is `import.meta.url.includes("$bunfs")` — whether this module is served from Bun's embedded filesystem — because that is the one fact about the process an environment variable cannot forge. release/ derives it locally instead of importing RUNS_FROM_COMPILED_BINARY from embedding/subprocess-command.ts: the upgrade path must not drag the rest of the program in behind it. A source checkout still honours the override, which is what lets the test suite drive the whole flow over a local HTTP server, and costs nothing because runUpgrade refuses to install from a checkout at all. That also means the refusal itself is only observable in a real compiled binary, so scripts/compiled-smoke.ts asserts it.

Related, same reasoning: the /releases/latest redirect is only followed while it stays on the origin's own host (its path may move — GitHub answers a renamed repository that way), a tag must match a release-name pattern before it reaches a URL, and both downloads are capped so a body that never ends is refused instead of read into memory. The origin is printed before anything is fetched.
