On POSIX an upgrade is one rename: the running process keeps the inode it started from, so renaming a new binary over the old one is safe. Windows refuses that — the loader holds a running image open without delete sharing, so the destination of the rename cannot be the executable currently mapped.

Renaming that image *away* is allowed, because a mapping follows the file and not its name. replaceBinary therefore performs two renames on Windows: the existing binary moves to "<target>.<pid>.old", then the staged one takes its name. Both or neither — a failure between them would leave the install directory with no cortex at all, so the second rename's catch puts the retired file back before rethrowing.

Deleting what was retired is the one step the process running that image cannot take, so the delete is best-effort and the file is expected to survive. discardOrphans already swept staging files an interrupted upgrade left behind, keyed by the pid in the name; the LEFTOVER pattern now covers ".old" as well, so the next upgrade reclaims it exactly the way it reclaims a ".partial" — and never touches one whose pid is still alive.

The staging name keeps an ".exe" tail on Windows (installerStagingPath). assertReportsVersion runs the staged file before anything is replaced, and Windows only launches a path it will treat as an image; without the tail the version probe would fail on every Windows upgrade and the feature would ship broken rather than absent.

Both branches take onWindows as a parameter defaulting to RUNS_ON_WINDOWS rather than reading process.platform inline. The suite runs on Linux, and a branch no test can enter is a branch the 100% coverage gate cannot see. replaceBinary is exported for the same reason: from installBinary the second rename cannot be made to fail once the first has succeeded, so the undo path is only reachable directly.

install.ps1 performs the identical two-step move, so a first install over an existing cortex.exe behaves the way an upgrade does.
