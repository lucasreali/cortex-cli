runGitHook swallows everything so it can never fail a commit, and SQLITE_BUSY was swallowed with the rest: a store another process was writing to meant the commit's decisions never landed until some later command happened to run — silently, with no record that anything was skipped.

Waiting it out is not the fix. bun:sqlite is synchronous and git is holding the user's terminal until the hook returns, so the default five-second busy_timeout would be five seconds of a hung commit. The hook opens with busyTimeoutMs 500 instead: long enough for the ordinary overlap, short enough that a person does not notice.

Past that it hands the work to a detached child rather than dropping it — `embed --missing` when the event embeds, `sync` when it does not. Both reconcile on their way in, both start after git has let go, and both carry their own default busy timeout, so the retry costs the commit nothing. That reuses the detach the hook already had for the embed instead of inventing a queue.

The test holds a write lock with BEGIN IMMEDIATE across the commit, asserts the decision is absent when git returns, releases, and waits for the detached child to land it — it fails if the deferral is removed.
