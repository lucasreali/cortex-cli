Reading the code index reconciles it, so labelAnchors awaited a tree-sitter pass over the whole repository inside an MCP tool handler, with no timeout and no fallback. EXTRACTION_VERSION going 1 to 2 makes the first get_context after an upgrade force a full re-index, so the first post-upgrade call on a large repo outlived the client's patience and the agent got nothing — where FTS had already found the decisions.

The wait is now bounded by ANCHOR_INDEX_TIMEOUT_MS (2000 ms, the same budget the vector leg gets on the same request) and degrades to the `unknown` grade, which exists for exactly this: "the code index could not be read". Nothing is cancelled — LazyCodeIndex caches the pass in flight, so the abandoned reconcile finishes and the next request is graded rather than starting over.

Deliberately not applied to the other code-index readers. get_impact, save_decision and `cortex why --symbol` read the index for answers that have no honest degraded form: a blast radius, an anchor warning and a symbol lookup are either computed or absent. Grading is the one read where a truthful "unknown" is still useful output, which is what makes it the one read that may give up.

Rejected: refreshing in the background and serving the snapshot instead. That never fixes the case the deadline exists for — a cold index has no snapshot to serve.

withTimeout moved from embedding/ to support/ to make this legal without app/ importing a timeout from the directory that owns vectors; disposingOnTimeout stayed behind, because disposing a provider on timeout is an embedding rule, not a general one.
