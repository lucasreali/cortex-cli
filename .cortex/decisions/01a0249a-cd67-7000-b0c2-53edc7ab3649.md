The runtime minted one session id at startup and held it for its life. Under the CLI that is right — the process is the conversation — but the MCP server caches a runtime per project for as long as it is up, so a server running for a week was one session for the week.

That is not cosmetic. The ranking tiebreaker needs MINIMUM_CORROBORATING_SESSIONS = 2 distinct sessions before it may promote a decision, while a single passed-over event is enough to demote one. A server that can only ever be one session therefore accrues the negative signal and never the positive: the tiebreaker systematically demoted and could never promote. The recorder's once-per-session claim compounded it, folding a week of impressions into one.

SessionIdentity (src/support/session-identity.ts) mints a new id once the gap since the last call reaches SESSION_IDLE_MS, 30 minutes. A gap with no traffic is the only conversation boundary visible from inside the server: MCP carries no conversation id. It is measured on performance.now(), not the wall clock, so a system time change cannot mint or merge sessions — the same reasoning behind the decay horizon's clamp on skewed timestamps.

The identity rolls three things at once: the events the usefulness log records, the query log's session column, and the session node ensureSession() creates — so GENERATED_IN points at the conversation that saved the decision rather than at the one that happened to open the runtime. UsefulnessRecorder drops its claimed set when the session changes, which is both what makes the same decision recordable again and what bounds that set for a long-lived process.

The recorders take a SessionSource ({ current(): string }) rather than a string, so usefulness/ and querylog/ stay independent of how the identity is minted.

Rejected: keying the session off an MCP client id (there is none), and leaving it per-process and lowering the corroboration threshold (that would weaken the asymmetry the threshold exists to enforce).
