A migration's 'already applied?' check and the write that answers it now share one BEGIN IMMEDIATE transaction, with the re-check inside it; the cheap check outside stays as a shortcut. A deferred transaction takes no write lock until its first write, so on a fresh store two processes both read 'not applied' and the loser ran DDL that was no longer valid — measured at 16 crashes in 36 runs across 12 fresh stores. With the write lock taken up front, busy_timeout makes the loser wait and the re-check makes it do nothing.

busy_timeout alone was not enough, and that is the part worth remembering: openDatabase sets it before anything that can need a lock, but SQLite does not run the busy handler for the switch to WAL — verified, it throws SQLITE_BUSY in 0 ms with busy_timeout at 5 s. So the switch is retried in a bounded loop instead, and because the journal mode belongs to the file rather than the connection, every process after the first only reads it back. Rejected: leaving the pragma order alone and treating 'database is locked' as acceptable on first use — this is the ordinary first-command-in-a-fresh-clone path, where the MCP server, a CLI invocation and the post-commit hook all arrive together.

Which process applies which migration is deliberately not fixed: the loser of one may win the next, and the invariant is only that each migration runs exactly once.
