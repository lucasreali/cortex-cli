The incremental pass rewrote rows only for files whose own bytes changed, but an import's target is a function of the whole file set, not of the file that spells the import. So an edge resolved — or left NULL — at index time was frozen until that importer happened to change or someone ran --force: adding a module never repaired the imports that were waiting for it, and `git mv util.ts util.tsx` left every edge into it pointing at a file that was gone. Both are invisible to doctor, because the importer really is unchanged, and both make get_impact answer "no code impact" with confidence.

`CodeIndexer.repairEdges` now re-resolves every row of `imports` after the per-file pass and writes only the rows that moved (`CodeRepository.retargetImports`, reported as `IndexReport.repaired`). It runs only when the file set actually moved — a path was added or removed — so a re-check on an untouched tree stays a stat per file, which is what the LazyCodeIndex window depends on. Removal is covered by the same pass, so `removeFile` still only deletes `from_path` rows.

`danglingTargets` is the same question asked of a store nobody reconciled, and it is what doctor reports: an edge whose target is absent from the listing. It is checked against the listing rather than against `files`, because an oversized source is deliberately a real import target with no `files` row.
