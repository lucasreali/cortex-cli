readCortexBinary parses the ustar header itself, and it trusted the declared size: Number.parseInt of a non-octal field is NaN, which slices to nothing and installs a zero-byte cortex over a working one; a size reaching past the end of the archive installs a truncated binary; GNU's base-256 encoding for sizes over 8 GB reads as a small octal number, because the high bit of the first byte is invisible to parseInt.

The size is now accepted only when it is a safe non-negative integer, the field does not carry the base-256 marker, and the member it declares ends inside the archive. The cortex member must also carry a regular-file typeflag ("0", or NUL for the original tar format). The extension typeflags ("x", "g", "L", "K") are refused for the same reason the others are: they carry a name or size that overrides the block after them, and a reader that does not honor them must not unpack the block they were there to correct.

This is defence in depth, not the primary control — the asset is checksum-verified and the origin is now allowlisted — but the reader runs before anything else looks at those bytes, and every one of these failures used to end in an executable being written.

tests/release/tarball.ts, the fixture that mirrors `tar --format=ustar`, wrote a nine-byte checksum into an eight-byte field and so put a space where every member's typeflag belongs; it takes an explicit typeflag and raw size field now, which is what lets these cases be pinned at all.
