listByFileAnchorOrSymbol was the fourth producer of a symbol name and the one the single normalizer did not reach: it compared two anchors with `a.symbol = ?` inside decisions.db, which stores an anchor verbatim and holds no normalized key. Two spellings of one symbol never met — the class of bug the shared recipe closed everywhere else.

Decided: keep the file half of the query in SQL and hand every anchor on that file to symbolKey in TypeScript.

Rejected: a symbol_key column on anchors (the 006- migration slot is still free). It was the tempting fix and the wrong one — stored derived state, free to go stale against src/support/symbol-key.ts, and needing its own staleness story the way a content_sha column would. anchors is small enough that a widened scan plus a TypeScript filter costs nothing, and that cost is the explicit trade-off accepted here.

Consequences: SELECT DISTINCT had to go, because projecting the anchor column makes sibling rows of one decision differ; a Map keyed by node id dedupes instead and preserves the previous ordering exactly. The file-level anchor ('') is still compared raw rather than through symbolKey, so a symbol whose spelling merely normalizes to empty is not silently promoted into a file-level anchor. EXTRACTION_VERSION was deliberately not bumped: this change writes nothing, so a re-index would fix nothing and would cost every user one.
