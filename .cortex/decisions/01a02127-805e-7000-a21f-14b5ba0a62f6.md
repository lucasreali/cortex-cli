The pass chooses its mode before reading anything: a full rebuild when `files` is empty, when the stored EXTRACTION_VERSION does not match this binary's, or when --force is passed; incremental otherwise. A full pass wipes and rebuilds inside one transaction and re-stamps the version, which is what makes a bump the only way to correct content an older extractor wrote.

Incremental staleness is (size, mtime, ctime), and the hash confirms rather than decides: a file whose triple moved is read and hashed, and an unchanged hash only refreshes the row (`touchFile`) instead of re-extracting. ctime is in the triple because size and mtime are both forgeable by an ordinary restore — `cp -p`, `tar -x`, `rsync -t`, a CI cache restore land new content under the recorded mtime, and a same-length edit keeps the size, after which the index served symbols that no longer exist and doctor reported "in sync". No userspace call can set an inode's change time. A ctime that moves without the content moving costs one read; the reverse costs correctness.

`computeDrift` reads the same triple through the same `isUnchanged`, because doctor reporting drift and index acting on it have to agree on what stale means or doctor calls a stale index clean.
