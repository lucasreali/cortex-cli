daemonPathsFor returned three paths in one directory: <model>.sock, <model>.lock and <model>.log. Windows has no socket file to place beside the other two — a named pipe is a name in a namespace the kernel owns, created and removed with the process listening on it — so on Windows socketPath becomes \\.\pipe\cortex-<owner>-<model> while lockPath and logPath stay files. They have to: the lock is what a second process reads to discover the daemon at all, and the log is where the worker's model-download progress lands.

The owner is part of the pipe name because that namespace is machine-wide, not per-user like a directory chmodded 0700. Without it two accounts on one machine would resolve to the same pipe, race for the daemon role, and the loser would be handed the other user's daemon. The name comes from USERNAME, which Windows sets for every interactive and service account; where it is somehow unset the fallback is a shared name, which is still better than no daemon — the hello handshake already refuses a peer serving another model or version.

Nothing about the degradation ladder changes. A pipe that cannot be reached is answered "unreachable" by probeDaemon exactly as a missing socket is, which is the rung the private worker already covers. The daemon's chmod of the directory and of the socket, and its unlink of a stale socket file, are already wrapped in try/catch and become no-ops there; the per-user isolation a 0700 directory gave on POSIX is what the owner in the pipe name replaces.

onWindows is a parameter defaulting to RUNS_ON_WINDOWS, not a process.platform read inline, so the suite — which runs on Linux — can drive the branch the 100% coverage gate would otherwise never see.
