findSymbol answers "where else does this name live?" with a full scan of `symbols` plus an NFKD normalize, a case fold, a regex and a split per row. That is forced: SQLite cannot run the recipe and no symbol_key column may exist, so the comparison happens in TypeScript. It is the right trade for one lookup and the wrong one for IndexedAnchors.confidenceOf, which needs it for every anchor that is not already `exact`, over every decision get_context, get_impact and `cortex why` return — a full scan and a full re-normalize per anchor, scaling linearly with repo size precisely where the product is most useful.

SymbolTable is that same read as a first-class collection: one scan, one symbolKey per row, every later name answered from the map. IndexedAnchors builds it on the first anchor that needs it and keeps it for the rest of the request, so a payload whose anchors all resolve exactly still never touches it. findSymbol is now the single-name shorthand for the same read, which is what keeps the two from disagreeing.

Per resolver, and never cached on CodeRepository: the table is a copy of a store that reconciles underneath it, and a resolver lives for one request. The rule that no normalized key is ever stored is untouched — the map is in memory, built from the canonical spellings the index holds.

Measured on a synthetic 60,000-symbol index with 25 anchors to grade: 2071 ms of scanning becomes 69 ms.
